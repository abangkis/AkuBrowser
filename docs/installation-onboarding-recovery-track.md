# Jalur khusus: instalasi, pemulihan, dan onboarding pengguna baru

Status: **INST-01 memiliki pemulihan kode generik. INST-02–05 memiliki mitigasi kode/panduan. Seluruh isu tetap menunggu penerimaan alur instalasi pada paket berikutnya; belum ada RC baru.**
Tanggal laporan: 5 September 2026. Konteks: pengujian instalasi AkuBrowser v0.9.0 RC3 pada lingkungan pengguna.

Keputusan pengguna, 13 September 2026: investigasi layar putih pada peluncuran pertama (INST-02) diparkir sementara agar isu lain dapat dilanjutkan. Avast ada di kedua perangkat yang mengalami gejala, tetapi belum ada log yang mengaitkan Avast dengan kejadian terkini; jangan nyatakan sebagai akar masalah atau ubah pengecualian antivirus. INST-03 tetap memerlukan penerimaan alur peluncuran pertama dan belum dapat dinyatakan selesai hanya dari peluncuran kedua yang normal.

## Tujuan

Menangani perjalanan instalasi sampai pengguna memperoleh akses sumber sebagai satu jalur perbaikan. Instalasi yang berhasil menyalin binary belum berarti pengguna berhasil memakai produk. Pengguna harus memahami status, hambatan, dan tindakan berikutnya tanpa mencari residu sendiri, menebak perlunya Chrome, atau mencoba restart tanpa arahan.

Dokumen ini mencatat laporan, bukti, kebutuhan mitigasi, dan kriteria penerimaan. Persetujuan perbaikan kode diberikan kemudian; itu bukan persetujuan untuk menghapus data pengguna, memindahkan sesi Chrome, mengubah arsitektur browser, atau membuat RC tanpa verifikasi penerimaan.

## Urutan kejadian yang dilaporkan

1. Instalasi/startup berulang kali gagal dengan ketidakcocokan schema database: pengguna melaporkan schema lama 5, sedangkan runtime baru membutuhkan 25.
2. Setelah mencari residu instalasi dan membersihkannya, aplikasi dapat terinstal dan menyala. Lokasi serta isi residu yang dibersihkan belum tercatat; jangan menganggap tindakan tersebut sebagai prosedur pemulihan yang sudah tervalidasi.
3. Peluncuran berikutnya tertahan pada layar putih. Banner Chrome for Testing menampilkan tautan **Download Chrome**, tanpa panduan AkuBrowser yang menjelaskan langkah selanjutnya.
4. Karena bingung, pengguna menutup lalu membuka aplikasi. Setelah itu halaman **Grant access** muncul. Penyebab perbedaan peluncuran pertama dan kedua belum diketahui.
5. Pengguna harus login ulang karena sesi Chrome yang biasa dipakai tidak tersedia di profil AkuBrowser. Ini dilaporkan sebagai hambatan adopsi yang besar karena pengguna mengandalkan sesi Chrome yang sudah login.

## INST-01 — Residu dan schema lama: kegagalan harus bisa dipulihkan

Prioritas: tinggi, menghalangi penggunaan.

Implementasi kode setelah laporan RC3 (belum menjadi bukti penerimaan pada instalasi pengguna): launcher meminta Sidecar aktif menginspeksi database yang ada sebelum startup. Sidecar yang sama mengklasifikasikan database sebagai tidak ada, kompatibel, dapat dimigrasikan melalui rantai migrasi lengkap, tidak didukung, lebih baru, atau tidak dapat diverifikasi. Database kompatibel dipertahankan; keadaan lain menawarkan hanya tindakan yang sesuai. Migrasi dan mulai baru membutuhkan keputusan eksplisit serta identitas database yang tidak berubah sejak inspeksi. Migrasi dilakukan pada salinan bertahap; mulai baru mengarsipkan database lama dan file SQLite terkait, tanpa menghapus profil browser. Jika pemeriksaan, penguncian, cadangan, atau migrasi gagal, aplikasi tidak melakukan reset otomatis. Error tetap terlihat dalam dialog Windows dan tersimpan di `data/database-recovery.log`; dialog dapat disalin memakai Ctrl+C. Jalur persiapan saat ini hanya tersedia pada Windows; perilaku non-Windows gagal tertutup. Uji unit dan CLI terbatas lulus, tetapi alur installer/launcher dalam paket RC dan pemulihan arsip oleh pengguna belum divalidasi.

Uji paket lokal 14 September 2026: fixture SQLite schema 5 dibuat hanya di `AkuBrowser/build/acceptance-db-schema5-20260914`; Sidecar **dari paket uji baru** menjalankan `--database-inspect` dan melaporkan `unsupported`, schema 5, target 25, serta fingerprint tersedia. Exit code 0 dan SHA-256 database sama sebelum/sesudah inspeksi. Ini membuktikan klasifikasi generik pada binary paket tanpa memutasi fixture; dialog Windows, pilihan keep/fresh melalui UI, dan installer aktual masih perlu uji terpisah. Database pengguna tidak diakses.

Pada salinan fixture yang terpisah di `AkuBrowser/build/acceptance-db-schema5-fresh-20260914`, tindakan CLI `--database-action fresh --database-confirm --database-expected-fingerprint` dari binary paket keluar 0: database aktif menjadi tidak ada, arsip muncul di dalam root fixture, dan SHA-256 arsip cocok dengan database semula. Ini membuktikan arsip pemulihan pada jalur CLI yang dikonfirmasi, bukan bahwa dialog Windows menyampaikan pilihan dengan jelas atau bahwa instalasi pengguna aman tanpa uji lanjut.

Pada salinan fixture lain di `AkuBrowser/build/acceptance-db-schema5-unconfirmed-20260914`, tindakan `fresh` tanpa `--database-confirm` ditolak; database tetap ada dan SHA-256 tidak berubah. Pada saat pemeriksaan CLI ini, fixture asli belum dipakai untuk uji dialog; hasil uji dialog berikutnya tercatat di bawah. Pemeriksaan ini memperkuat gerbang persetujuan eksplisit pada binary paket, tetapi belum menggantikan penerimaan interaksi Windows.

Kasus generik tambahan pada binary paket: fixture schema 26 diklasifikasikan `newer` terhadap target 25, dan percobaan migrasi terkonfirmasi ditolak tanpa mengubah hash database. Fixture berisi data non-SQLite diklasifikasikan `unknown` dengan fingerprint; startup normal tanpa keputusan pemulihan ditolak sebelum server terbuka, hash tetap sama. Semua fixture berada di direktori build terpisah. Ini membuktikan fail-closed untuk versi masa depan dan data rusak pada jalur CLI, bukan hasil dialog/installer.

Masalah: pengguna hanya mengalami kegagalan/keluar tanpa pesan yang membantu dan harus menemukan residu sendiri. Binary baru tidak otomatis berarti database lama kompatibel.

Kebutuhan perbaikan:

- Deteksi database yang sudah ada serta schema aktual sebelum aktivasi runtime; tampilkan kompatibilitas dan tindakan yang tersedia.
- Jelaskan schema ditemukan, schema tujuan, lokasi data, apakah migrasi didukung, dan alasan aplikasi belum dapat dibuka menggunakan bahasa pengguna.
- Untuk schema tidak didukung, sediakan pemulihan terpandu yang melindungi data: cadangan terverifikasi, pilihan mempertahankan data, serta pilihan mulai dengan data baru yang membutuhkan persetujuan eksplisit dan menjelaskan dampaknya.
- Jangan menyarankan mengubah angka schema secara manual atau menghapus seluruh folder sebagai solusi umum. Penanganan database dan profil browser harus dibedakan agar pemulihan database tidak ikut menghilangkan sesi login.
- Tampilkan error yang tetap dapat dibaca, tombol menyalin diagnostik, lokasi log, dan langkah mitigasi. Pengguna tidak boleh harus membaca terminal yang segera tertutup.

Mitigasi sementara yang perlu dipandu: identifikasi lokasi data dan error aktual, cadangkan data sebelum tindakan, lalu tentukan apakah data lama harus dipertahankan atau pengguna menyetujui database baru. Keberhasilan pembersihan pada laporan ini bukan izin untuk mengulang penghapusan pada pengguna lain.

Kriteria penerimaan: uji instalasi bersih, upgrade schema yang didukung, residu schema 5, database bermasalah, dan pembatalan pemulihan. Setiap kegagalan menampilkan alasan dan tindakan berikutnya; data tidak berubah tanpa jalur yang diizinkan; mengulang instalasi tidak menjebak pengguna pada kegagalan yang sama tanpa penjelasan.

## INST-02 — Layar putih dan banner Download Chrome

Prioritas: tinggi, menghalangi onboarding dan mengarahkan tindakan yang salah.

Mitigasi kode setelah laporan: app shell dan pembuka halaman internal menambahkan `--disable-infobars` untuk banner informasi Chrome for Testing, sesuai dokumentasi Chromium. Dokumen HTML awal memuat status persiapan dan tautan muat ulang; skrip watchdog terpisah dari modul aplikasi memberi status tahap tetap bila aset, pemulihan state, atau rendering gagal/terlalu lama. Bootstrap memberi tanda siap setelah UI dirender dan menyembunyikan panel pemulihan. Ini belum membuktikan penyebab layar putih awal: navigasi yang sama sekali gagal menerima HTML tidak dapat ditangani oleh fallback di dalam HTML. Upaya pemeriksaan Chromium terpin secara headless pada lingkungan pengembangan ini berhenti di proses GPU sebelum DOM tersedia, sehingga bukan bukti visual produk. Peluncuran pertama dan keadaan pasca-onboarding masih harus diperiksa pada paket uji berikutnya tanpa mengambil alih profil pengguna.

Bukti upstream untuk flag: [delegate Chrome for Testing](https://chromium.googlesource.com/chromium/src/+/main/chrome/browser/ui/startup/chrome_for_testing_infobar_delegate.cc) memakai teks tautan `Download Chrome` dan tidak memiliki tombol; [pengelola infobar Chromium](https://chromium.googlesource.com/chromium/src/+/main/components/infobars/core/infobar_manager.cc) menekan infobar tanpa tombol ketika `--disable-infobars` aktif pada Chrome for Testing, sambil tetap mengizinkan infobar yang punya tombol. [Uji browser Chromium](https://chromium.googlesource.com/chromium/src/+/refs/tags/132.0.6834.222/chrome/browser/chrome_for_testing/chrome_for_testing_info_bar_browsertest.cc) juga memeriksa banner tidak tampil pada tab pertama maupun tab baru dengan flag itu. Bukti sumber ini mendukung mekanisme, tetapi tidak menggantikan pengamatan visual pada Chromium terpin yang dikemas AkuBrowser.

Uji UI terisolasi, 13 September 2026: Sidecar kode terbaru dijalankan tanpa app shell pada port dan database uji sementara; browser dalam aplikasi yang tersembunyi menampilkan `AkuSidecar ready` serta halaman `Connect AkuBridge first` pada kunjungan pertama dan setelah reload. Ini membuktikan HTML/aset/bootstrap dapat merender tahap awal tanpa Bridge pada browser uji, bukan bahwa Chromium terpin/installer atau alur izin sumber sudah lulus. Tab, proses Sidecar, dan database uji ditutup/dibersihkan sesudah pemeriksaan.

Tuple uji lokal (bukan RC/installer) dibangun dari tiga worktree yang masih kotor di `AkuBrowser/build/acceptance-inst02-05-20260913`. Builder memverifikasi struktur, hash Chromium 152.0.7977.54, dan launcher; payload berisi 386 file. Sidecar yang benar-benar berada dalam tuple tersebut juga menampilkan `Production · Installed app`, `AkuSidecar ready`, dan panduan `Connect AkuBridge first` pada browser uji tersembunyi sebelum dan sesudah reload. Karena browser uji tidak memuat AkuBridge dan bukan Chromium terpin, keadaan `AkuBridge reconnecting` di sini diharapkan dan tidak boleh dianggap sebagai hasil penerimaan Bridge. Tuple lokal ini belum dipasang atau dipublikasikan.

Tuple yang sama dibangun ulang setelah perbaikan status sesi, flag halaman internal, copy/validasi Gemini, dan isolasi namespace kredensial uji; verifikasi launcher paket `--verify-only` lulus. SHA-256 launcher `c13848edbd72d8d6c6ba1b42129ea2307ae19b156122cd2b79ff844d7bbc9a4e`, Sidecar `d1a08119a5dd45713d92e97f238a363dbb719658d5acc7a0db6b9f5b5f27487c`, dan Chromium terpin `b0123437c55a3893e8988328f576ffcbe68cee7743d3653ffe865c73633b1ef4`. Karena dibangun dengan `-AllowDirty`, tuple ini tetap artefak uji lokal, bukan kandidat rilis yang memenuhi gerbang sumber bersih.

Uji app-shell terpin 13 September 2026 menemukan batas panjang perintah relaunch Windows: tuple uji pada path panjang gagal menetapkan property 2 dengan `HRESULT 0x8007007a`, sedangkan tuple yang sama melalui alias path pendek berhasil membuka jendela. Launcher kini menghilangkan argumen `--install-root` yang redundan bila executable berada langsung di root instalasi; argumen tetap dipakai untuk root alternatif. Tes launcher lulus. Tuple uji baru di `AkuBrowser/build/acceptance-inst02-05-relaunch-20260913` (launcher SHA-256 `a649bf3449444563c306e14b0480d6b2837c7faaa8185d1f08769a59358f09e2`) berhasil membuka app-shell dari path panjang asli. Alias path pendek sementara telah dihapus, tuple sumber tetap ada. Ini membuktikan perbaikan error relaunch pada jalur uji tersebut, bukan penerimaan installer menyeluruh.

Pada dua profil uji yang benar-benar baru, peluncuran **pertama** tetap menampilkan jendela putih dengan judul awal `127.0.0.1_/` lebih dari 90 detik; `/api/health` tetap `ok`, HTML awal HTTP 200 mengandung panel statis/watchdog, dan Bridge tetap `reconnecting`. Peluncuran **kedua** pada profil yang sama menampilkan onboarding normal tanpa banner, dan Bridge menjadi `healthy`/kompatibel; screenshot dan konfirmasi pengguna mendukung keadaan visual itu. Profil kosong lain yang dijalankan tanpa extension Bridge juga putih. Uji GPU-off terpisah juga putih. Jadi penyebab belum terbukti, tetapi bukan sekadar menunggu 90 detik, bukan syarat adanya extension, dan tidak dapat diselesaikan oleh watchdog JS ketika dokumen awal belum dirender. Jangan menandai INST-02/03 diterima atau menambah restart otomatis sebelum ada bukti startup Chromium/navigasi/renderer yang lebih langsung. Semua jendela/proses uji ditutup; Chrome pribadi tidak disentuh.

Untuk langkah diagnosis berikutnya, app-shell kini punya log startup Chromium **opt-in khusus namespace profil uji**. Skrip penerimaan menerima `-ChromiumStartupDiagnostics`; setelah Sidecar baru dikemas ulang, mode ini mengaktifkan `--enable-logging` dan menulis `chrome-startup.log` di profil terisolasi. Tuple uji yang dipakai sebelumnya dibuat **sebelum** opsi diagnostik ditambahkan dan tidak memuatnya. Mode normal tidak menyalakan log tersebut; tes unit membuktikan guard dan argumennya, dan `-PlanOnly` berhasil tanpa membuka jendela. Ini alat diagnosis, bukan perbaikan layar putih. Isi log harus diperlakukan sensitif bila nanti sumber uji pernah login. [Panduan Chromium untuk logging](https://chromium.googlesource.com/playground/chromium-org-site/+/refs/heads/main/for-testers/enable-logging/index.md) dan [implementasi logging Chromium](https://chromium.googlesource.com/chromium/src/+/HEAD/chrome/common/logging_chrome.cc) mendukung flag/log file tersebut.

Uji diagnostik opt-in berikutnya, 13 September 2026: tuple baru `AkuBrowser/build/acceptance-inst02-05-diagnostics-20260913` (launcher SHA-256 `a649bf3449444563c306e14b0480d6b2837c7faaa8185d1f08769a59358f09e2`, Sidecar `d5093d57d58c3bf7ef36ed9ce020027b6d37c4e30a73a293f2e8c72db7a1ed8b`) berhasil meluncurkan satu app-shell terpin pada profil kosong. Log profil uji mencatat `Sandbox cannot access executable ... chrome.exe ... Access is denied (0x5)` di proses browser, lalu `Network service crashed or was terminated, restarting service`. Log terakhir sekitar tiga detik setelah start; backend tetap sehat dan Bridge `reconnecting` sekitar 90 detik kemudian. Chromium melakukan `AppContainer::AccessCheck` untuk baca/eksekusi executable sebelum menyalakan proses sandbox; [kode Chromium](https://chromium.googlesource.com/chromium/src/+/c98af87039d818ab3ff734c1262244d5aaa96710/sandbox/policy/win/sandbox_win.cc) mendukung interpretasi error ini. [Panduan sandbox Chromium](https://chromium.googlesource.com/chromium/src/+/main/docs/design/sandbox.md) menyebut ACE khusus pada binary/data yang diakses LPAC. ACL biasa pada exe uji mengizinkan `BUILTIN\Users` membaca/mengeksekusi, tetapi tidak menampilkan ACE `ALL RESTRICTED APPLICATION PACKAGES`. Hubungan kausal error ini dengan layar putih **belum terbukti**: tidak ada perbandingan log peluncuran kedua maupun paket yang terpasang di lokasi instalasi normal. Jangan mengubah ACL sistem, menonaktifkan sandbox, atau menambah restart otomatis berdasarkan satu log ini. Proses uji ditutup dan diverifikasi tidak tersisa; Chrome pribadi tetap berjalan.

Perbandingan ACL baca-saja tambahan: `C:\Program Files\Google\Chrome\Application\chrome.exe` memiliki `ALL APPLICATION PACKAGES` serta `ALL RESTRICTED APPLICATION PACKAGES` read/execute, sedangkan `C:\Users\Force\AppData\Local\Programs` (default root NSIS AkuBrowser) hanya mewariskan SYSTEM, Administrators, dan akun pengguna; skrip installer AkuBrowser tidak tampak menambahkan ACE LPAC. Ini meningkatkan kekhawatiran bahwa instalasi normal juga bisa terkena, tetapi belum membuktikan bahwa ACL adalah satu-satunya sebab first-run putih. Langkah kausal berikutnya harus membandingkan profil baru dari paket terpasang atau artefak uji yang diberi ACE baca/eksekusi **hanya pada Chromium runtime**, dengan persetujuan eksplisit sebelum perubahan izin lokal tersebut.

Eksperimen ACL yang disetujui pengguna, 13 September 2026: hanya salinan `runtime/versions/0.9.0/chromium/bin` dalam tuple diagnostik lokal di atas (318 entri, tanpa reparse point) mendapat ACE read/execute untuk `ALL APPLICATION PACKAGES` (`S-1-15-2-1`) dan `ALL RESTRICTED APPLICATION PACKAGES` (`S-1-15-2-2`); readback `chrome.exe` mengonfirmasinya. Tidak ada ACL instalasi atau profil pengguna yang diubah. Satu profil kosong baru `AkuBrowser/build/acceptance-profile-acl-20260913` dijalankan tanpa Bridge pada port diagnostik 18123. App-shell keluar sendiri sekitar satu detik kemudian, dan port tertutup. Log Chromium **tidak lagi** berisi `Sandbox cannot access executable`; sebaliknya network service crash, proses GPU berulang kali keluar dengan kode `-1073741790` (`0xC0000022`, access denied), lalu browser berhenti dengan `GPU process isn't usable. Goodbye.` Ini membuktikan ACE tersebut menghilangkan kegagalan preflight executable yang teramati, tetapi **tidak cukup** untuk menyembuhkan startup pertama. Jangan menganggap error registry/cursor lain sebagai akar penyebab tanpa jejak akses yang lebih tepat; jangan memperluas ACL ke data pengguna atau mematikan sandbox. Tidak ada jendela uji kedua yang dibuka pada eksperimen ini.

Konsultasi Astra Medium atas eksperimen ini: preflight executable hanya memeriksa akses baca/eksekusi pada `chrome.exe`, bukan seluruh DLL, driver, data profil, atau registry; proses GPU yang keluar dengan access denied belum tentu memakai AppContainer/ACE yang sama. Kode Chromium terpin 152.0.7977.54 tidak mengaktifkan AppContainer untuk GPU lewat keputusan yang sama dengan network service. Keberhasilan peluncuran kedua pada profil lama tetap belum terjelaskan. Pemeriksaan read-only CodeIntegrity/AppLocker tidak menemukan event pada interval peluncuran terakhir, tetapi itu tidak menyingkirkan penolakan filesystem. Bukti berikutnya yang bernilai adalah trace singkat satu peluncuran profil baru, difilter pada executable Chromium uji dan anak prosesnya, untuk mengidentifikasi akses spesifik yang ditolak. Trace proses/file/registry semacam itu dapat mengandung path dan command line sensitif serta mungkin memerlukan binary resmi ProcMon dan elevasi; jangan memulainya tanpa persetujuan cakupan baru. Jangan mempromosikan eksperimen ACL ini menjadi perubahan installer sebelum target penolakan dan perbaikan terbatas tervalidasi.

Uji sumber installer memeriksa urutan aktivasi tuple, shortcut launcher, batas kepemilikan file, serta opsi full reset profil dan lulus sampai gerbang verifikasi tuple. Verifikasi installer resmi menolak tuple tersebut karena sumbernya masih kotor; hasil itu adalah kebijakan rilis yang diharapkan dan bukan kegagalan INST-02–05. Belum ada installer atau RC baru yang dibuat.

Uji kegagalan aset, 13 September 2026: fixture loopback `AkuSidecar/test/fixtures/startup-watchdog-browser-fixture.mjs` menyajikan HTML/CSS/watchdog yang sama sambil sengaja mengembalikan 404 untuk `app.js`. Browser uji tersembunyi menampilkan panel `AkuBrowser could not finish opening`, tahap `interface assets`, serta tautan reload dan penjelasan bahwa Chrome tidak perlu diunduh. Ini membuktikan fallback terlihat ketika HTML sudah diterima tetapi modul aplikasi gagal dimuat; bukan uji navigasi yang gagal sebelum HTML, Chromium terpin, atau instalasi nyata. Fixture dan tab dihentikan setelah uji.

Masalah: proses backend dapat hidup sementara halaman produk kosong. Banner browser menjadi satu-satunya arahan yang terlihat, sehingga pengguna dapat menyimpulkan bahwa mereka harus mengunduh Chrome.

Tambahan bukti pengguna, 5 September 2026: setelah onboarding berhasil dilewati, banner **Chrome for Testing** beserta tautan **Download Chrome** tetap muncul. Foto terbaru memperlihatkan halaman **Settings** AkuBrowser sudah dirender, dengan pengaturan sumber terlihat di bawah banner. Artinya masalah banner juga terjadi saat UI sudah dapat digunakan; penyelesaiannya tidak boleh bergantung pada perbaikan layar putih atau dianggap selesai ketika onboarding berhasil.

Referensi foto tambahan lokal sesi: `.codex-remote-attachments/01a07138-1baa-7cd1-9e0b-32c6a596c84f/75fc2188-54b6-4fb2-9dc9-911a0bf8acef/1-Photo-1.jpg`, relatif terhadap AkuWorkspace. Keberhasilan melewati onboarding berasal dari laporan pengguna; tampilan Settings dan banner didukung foto. Belum ada bukti pengguna benar-benar mengklik tautan unduhan.

Kebutuhan perbaikan:

## INST-03 — Perjalanan ke Grant access terputus dan bergantung restart

Prioritas: tinggi, satu rangkaian dengan INST-02.

Mitigasi kode: AkuBridge sekarang membatasi dan mengulang injeksi relay yang gagal sementara tab tepercaya sedang bernavigasi, termasuk pada event tab selesai berikutnya; tab baru ditandai pulih setelah injeksi dan ping sukses. Saat pengguna kembali ke jendela AkuBrowser, UI meminta ulang status Bridge dan sesi sumber tanpa menunggu interval ping berkala; probe sesi yang tidak dijawab berakhir dengan pesan dan dapat dicoba lagi. Kegagalan probe global kini mengganti hasil sesi lama dengan status belum terkonfirmasi, tanpa menyatakan nol tab atau mengubah izin Bridge. Ini menutup beberapa jalur state yang bisa tertinggal, tetapi belum membuktikan bahwa jalur tersebut penyebab tunggal laporan Grant access baru terlihat setelah restart. Uji perjalanan peluncuran pertama tetap diperlukan.

Masalah: halaman Grant access baru terlihat setelah pengguna menutup dan membuka ulang aplikasi tanpa panduan. Pemulihan kebetulan ini belum merupakan perjalanan produk yang dapat diterima.

Kebutuhan perbaikan:

- Definisikan satu urutan yang terlihat: instalasi selesai → runtime siap → UI siap → Grant access → kesiapan sumber → siap digunakan.
- Simpan progres onboarding dan pulihkan ke langkah yang benar setelah aplikasi ditutup, gagal, atau dibuka kembali.

Kriteria penerimaan: uji peluncuran pertama, buka ulang sebelum/sesudah pemberian akses, startup lambat, serta gangguan pada setiap tahap. Pengguna selalu tahu posisi dan langkah berikutnya; pemberian akses tidak harus diulang karena state yang hilang.
